# Norn — Build Log

One line per sub-checkpoint. A checkpoint is ✅ only when its "done when" is fully
true, the suite is green, and it is committed. Gates in `PLAN.md` are ticked only
when every line of the gate is true.

Method (binding): TDD (red → green → refactor), one package = one responsibility,
dependencies point inward (`cmd/` → `internal/*` → stdlib/crypto), interfaces at
boundaries only, no package imports a sibling it doesn't need. The **Python
reference implementation** under `contrib/norn-ref/` is written *from the spec,
first*, and generates the vectors the Go code must match — so the Go code never
becomes its own oracle.

## Phase 1 — Core library (Go)

Decision after 0.13b: start Phase 1 rather than run a fifth gate. Phase 1 *is* a
second implementation of §4 and §5, so it surfaces spec gaps as a side effect of
being useful, and `PLAN.md` already schedules a cold-model gate at Phase 6
against the frozen spec.

Rule for this phase: the Go code is written **from `SPEC.md`**, and the vectors
are the oracle. Where Go and the Python reference disagree, the spec decides —
and if the spec is silent, that is a defect to record, not a coin to flip.

## Decision taken — 2.9d: an `enroll` needs a device signature the device cannot make

**Answered 2026-09-19: option C.** The loop resumed at 2.9d-i.

**Raised 2026-09-19, before writing a line of `norn sign`.** The loop stops here
by its own rule: this changes the normative protocol and regenerates the whole
vector suite, so it is not mine to decide quietly.

**The contradiction.** `SPEC.md` §4.3 requires an `enroll` entry to carry a
`device` signature, and §4.2 says every signature is over *the entry's*
preimage — an envelope whose `ts`, `after` and body the **signer** chooses.
`ENROLLMENT.md` part 3 has the device print one QR and go quiet: it is headless,
it never sees that envelope, and `norn sign` is supposed to produce a **full**
`enroll` entry in one step. Both documents cannot be right.

**Why four gate runs and 208 tests missed it.** The fixture holds *every* private
key, so it signs one envelope as the device and again as a signer:
`_signed(env, [(device, "device"), ("signer1", "signer")])`. That is a signature
no real participant could produce, and nothing in a conformance suite can tell
the difference — the entry is valid either way. **The oracle was able to forge
consent, so the protocol was never asked to provide it.** The same shape as the
signature-blind replay of gate run 4, one level up.

Only `enroll` is affected: `rotate` and self-`revoke` are built **by** the
device, so it signs those envelopes itself.

| # | Option | What it costs |
|---|---|---|
| A | **Round trip.** Device → request → signer builds the entry → entry back to the device → device signs → submit. §4.3 unchanged. | Needs a return channel to a headless Pi, which is the thing this design exists to avoid. Kills the Phase 2 gate line "device QR → `norn sign` → submit → active, under 3 minutes". |
| B | **The device builds the entry.** `norn enroll` emits an `enroll` envelope already signed by the device; the signer appends signer signatures, which is legal because the preimage excludes `sigs`. §4.3/§5.1 unchanged. | An `enroll` can then never carry `after` — the device cannot know the log size — so the §4.4 ordering guard is lost for exactly the entry type that creates an identity. The signer can only accept or reject the device's labels and expiry. §16's request format, specified and vectored in 2.9a, is replaced by a partial entry. |
| C | **Embed the request (recommended).** The `enroll` body becomes the request bytes verbatim; §5.1's device check becomes "the embedded request decodes, its signature verifies under its own `device_pk`, and its `net` matches the entry's". | Normative change to §4.3, §5.1 and §5.2's wording; every `enroll` vector, `state.json`, `served/` and `proofs/` regenerate; both implementations change. Two or three checkpoints. |

**Why C is the recommendation.** It is not a workaround for A — it is a
*stronger* guarantee. A device signature over the envelope proves the device saw
some envelope; an embedded request proves the device consented to **exactly**
this `device_id`, `device_pk`, `wg_pk`, labels and expiry, and the signer cannot
alter any of them without destroying the proof. Meanwhile `ts` and `after` stay
where they belong, with the signer, who is the only party that knows the log.
The device keeps one job — say what it wants and prove it holds its key — and
the signer keeps one job — decide, and place the entry in the log.
- **2026-09-19 · 2.9d-i `enroll` carries the request (D-057) — the protocol change the blocked checkpoint asked for.**

That the facts are older than they look is said out loud (`ENFORCING_ON_STALE_STATE`) rather than left for an operator to infer.
  - **A tampered checkpoint is not a log outage — it is worse — and the table survives it too.** Appending a line to the signed note makes verification fail; the interface is untouched.
  - **A failed cycle does not republish `proven.json`.** A stale file would be worse than none, because it would look current.
  - **Observe is the default when no mode is set** (D-005), and a missing or unusable trust file means **refuse to start** in every mode — a node that started without an anchor would enforce nothing while looking like it worked.
  - Everything the agent touches is an interface, so these tests substitute a directory for a log and a fake for a kernel. Not one of them needs a WireGuard device.
  - Go: 36 packages, 325 tests; `go test` and staticcheck green.
- **3.5b `internal/wgdev` — the kernel, paid for once and fenced in (D-059).**
  - **Reordered before the daemon on purpose:** a `nornd` with nothing to drive cannot be run, and the dependency question had to be answered before a binary depended on the answer.

Taken anyway, because the alternative is hand-rolling **generic netlink** — family resolution, nested attributes, dumps — on a machine with no netlink to test against. That is the neighbour of D-053's rule: hand-write wire formats, never crypto primitives, and **never a kernel protocol you cannot test**. A mis-parsed peer list is a security failure, not a formatting bug.

- **3.5c `cmd/nornd` — a thin binary, and the defaults that are load-bearing.**
  - **The mode is announced before anything can fail.** An operator reading a startup error should already be able to see which mode was intended, because *"it did not start"* and *"it started enforcing"* are very different things to be wrong about. Observe also says what it will **not** do — "this node will alarm and write nothing" — and a test asserts owner mode never prints that line.

- **3.6 fight detection — telling a misconfiguration apart from a disagreement.**
  - **One eviction at a time, the two look identical.** A control plane that keeps putting the same key back is not misconfigured; it *disagrees* with the log about who belongs on the network, and an operator needs to be told that in those words. Three evictions in sixty seconds is the line (`ENFORCEMENT.md` part 3), and the message names the key, the count and the window rather than quoting a default that may not apply.
  - **A fight is declared once, not every poll.** A caller that takes an interface down on the signal must not do it five times a second. A run that dies down lapses, so a fresh run is a fresh fight — and Norn **keeps evicting throughout**: alarming is not giving up.
  - **A failed eviction is not evidence.** If the interface refuses the write, the key has not "come back" — counting it would blame the control plane for Norn's own inability to write. Evictions are recorded only after they succeed, and there is a test that runs five failing cycles and expects silence.
  - **Quarantine never happens by default.** `alarm` keeps the network up; `quarantine` takes the interface out of service until a human intervenes. Failing closed is a **choice**, and an agent configured to quarantine with no way to do it is **refused at startup** — finding that out mid-incident is too late. The daemon also warns at boot when the policy is armed.
  - **Quarantine runs a command an operator can read.** `ip link set {iface} down` on Linux, and nothing assumed anywhere else — taking a network down is a break-glass action, so the exact argv is in the config, in the logs, and replaceable with `wg-quick down` or a firewall rule. On a platform with no safe default, Norn says what to configure instead of guessing.
  - **The detector is bounded.** `nornd` runs for months on a Pi and an attacker can mint keys all day, so quiet keys are forgotten and the map is capped at 4 096 — tested by minting more than that.
  - Go: 39 packages, 364 tests; `go test` and staticcheck green.
- **3.8 the Phase 3 gate audit — no line ticked, and one that was never tested.**

- **4.1a cosignature keys — Norn could not have accepted a real witness, and found out by reading the spec first.**
  - **The defect, in three parts.** `c2sp.org/tlog-cosignature` says a witness key is algorithm **0x04**, and the byte is part of the key id — so the same public key under 0x01 and 0x04 is **two different verifiers**. Norn encoded witness keys as 0x01 (both implementations); `ParseVerifierKey` **refused** anything that was not 0x01, so `trust.Validate` would have **rejected a trust file naming a real witness**; and `note.Split` required a 68-byte signature line, so a cosigned checkpoint — which §6 says a checkpoint *is* — **would not have parsed at all**. Gate line 4.4 was not merely unimplemented, it was unreachable.
  - **Found before writing code, by fetching the format instead of recalling it.** Same habit as BIP-350 and RFC 7748: the spec named the algorithm byte, and the byte did not match what the project shipped.
  - **The cross-check was green because both sides were wrong the same way.** 2.1's ecosystem test required `x/mod/sumdb/note` to accept *every* key in the trust file, witnesses included — and sumdb only knows note keys. It passed because Norn was handing it note keys where witness keys belonged. It now splits honestly: the **log key** is checked against sumdb, the **witness keys** against `transparency-dev/formats/note`, which is what a real witness uses — and sumdb must **reject** them, or we are back where this started.
  - **Cosignatures verify against the ecosystem in both directions**, using the package a witness runs: their generator's key rendered by our renderer must be byte-identical, their signer's cosignature must verify here, and ours must open there. That is most of 4.4's substance, available without a witness process.
  - **A cosigned checkpoint must still verify under the log key alone** — the log's signature says this is the log, the cosignatures are additional — so unknown and cosignature lines are skipped rather than failed. An unknown witness is ignored (somebody else's business); a *trusted* witness's line that does not verify is an error (a claim that this network's witness said something it did not).
  - **Both rules are now normative and vectored**: §9.1 states the algorithms, and `trust-bad/15` and `16` are files that parse perfectly as verifier keys and are refused only by the algorithm rule.
  - The fingerprint moved, the guard from 2.8 caught it, and `SPEC.md`'s worked example was updated rather than left to rot.
  - Go: 40 packages, 375 tests; `go test`, staticcheck and both halves of `vectors-check` green.
- **4.1b `internal/policy` — the grammar, verified rather than remembered, and a consistency rule the file needed.**
  - **The published grammar turned out to match the shape Phase 0 guessed** — `log`, `witness`, `group <name> all|any|<k>`, exactly one `quorum`, `none` to opt out. That is a relief rather than a formality: 4.1a had just found a key encoding that was wrong in precisely the way an unverified guess is wrong, so the policy was checked against the specification before a line of parser was written.
  - **The parser is strict because a policy is where a network says how much corroboration it wants.** A line nobody understood is a requirement nobody is enforcing, so an unknown keyword, a forward reference, a duplicate key, a threshold larger than its group and a missing or second `quorum` are each errors. Fourteen refusals are tested by name.
  - **A cosigner nobody named counts for nothing**, however valid its signature — which is the property that makes a quorum mean anything. Two of three, `all`, `any` and nested groups are all exercised, and a repeated name is not two witnesses.
  - **`witnesses` and `policy` must now name exactly the same parties**, with the same keys. They are not redundant: `witnesses` is where a node learns a witness's *name and address*, `policy` is where it learns whether that witness *counts*. A file where they differ configures a quorum over parties the node cannot reach, or lists parties nothing requires — and either way the operator believes they set something they did not. Normative in §9.1, enforced in both implementations, and vectored as `trust-bad/17` and `18`.
  - **A vector that failed for the wrong reason was caught and fixed.** The first `17` used a key string edited by hand, so it was rejected for a broken key id rather than for the rule it is named after — the D-044 trap. It now carries a perfectly valid cosigner key under a name the policy never mentions, so only the agreement rule can reject it.
  - The shipped policy is checked to be usable *and* to need more than one witness: a homelab default whose quorum one machine could meet alone would have lost the only thing it was for.
  - Go: 41 packages, 383 tests; `go test`, staticcheck and both halves of `vectors-check` green.
- **4.1c the verifier enforces the quorum — and enforcing it proved Norn could not produce one.**
  - **§10 step 3 is real now.** A checkpoint is accepted only if every cosignature from a witness the policy *names* verifies, and the quorum is satisfied. Five refusals are tested by name: one cosignature short, none at all, cosignatures only from witnesses the policy never named, a forged line carrying a named witness's key id, and — the other direction — `quorum none` accepting an uncosigned head, because a network is allowed to ask for no corroboration and Norn does not get to overrule it.
  - **Each refusal was checked against a disabled check.** Stubbing `checkQuorum` to return "fine" turns all five red. A test that passes with the feature removed is a test of nothing, and this is the check most worth not accidentally disabling.
  - **Then it broke every end-to-end path, and that was the finding.** `cmd/norn`, `cmd/norn-log` and three package suites went red at once, all for the same reason: **nothing in Norn could produce a cosignature**, so every log it runs served heads that no correctly-configured node would accept. The verifier was not wrong; the product was half-built, and only enforcement made it visible. Shipping the enforcement without the other half would have been a release where `norn init` produces a network that cannot be verified.
  - **So `norn-log` learned `-self-witness name=keyfile`** — GOSSIP part 3's "same host as the log" row, which is independent of *nothing*, is allowed as a 1-of-1 in observe mode, and now says so on stderr every time it starts. It is the bootstrap and lab configuration; pushing to witnesses that run elsewhere is 4.3.
  - **It validates against the policy at startup**, because the failure it prevents is silent: a witness name the policy never mentions, or the right name under the wrong key, produces cosignatures nothing counts — a log that looks healthy to its operator and is refused by every verifier on the network. Both are refused before the listener opens. The flag takes the *policy's* short label (`pi`) and signs under the note name inside that witness's key (`norn-witness/pi`); they are two names for one party, and signing under the wrong one produces a line nothing matches.
  - **The store gained a `Cosigner` seam, which is the shape 4.3 plugs into.** `tlogstore` knows that a published head passes through corroboration; it does not know whether that is an HTTP round trip or a key in the same process.
  - **And it republishes its head on open** — a bug found by the E2E failure, not by a test. A log that gains a witness, or is restarted with different keys, was otherwise serving the checkpoint written under the *old* configuration until its next append: indefinitely, on a quiet log. The corollary is worth knowing: restarting `norn-log` without its `-self-witness` flags republishes an **uncosigned** head straight away, which is why it warns.
  - **A cosigner that fails fails the publish.** Writing the bare log-signed head instead would serve a checkpoint the network's own policy rejects, while looking exactly like a successful append. What a log should *do* about an unreachable witness — retry, serve stale, degrade — is 4.3's question; refusing to pretend is this one's.
  - **`norn-genlog` stopped cosigning by hand** and publishes through the same seam, so the fixture and a real log now take one path rather than two that must be kept in agreement. The regenerated `served/checkpoint` is byte-identical.
  - **The docs stopped overclaiming in one place and underclaiming in another.** §10's `# NOT YET IMPLEMENTED — Phase 4` is gone because the line is now true. §6 moved out of §12.1's "not vectored" table, with the caveat stated rather than skipped: the cosignature *format* is vectored and cross-checked against `transparency-dev/formats`, but these cosignatures come from keys the generator holds, so they prove the format is right — not that an unmodified witness will produce one. That is still 4.4.
  - **No Phase 4 gate line flips.** "Witness quorum lost → node refuses the new checkpoint, keeps last good, alarms" is a lab line: it needs witnesses that can be taken away. The software half is now true and tested, and the line stays open until the lab runs it.
  - Go: 40 packages, 392 tests; `go test`, staticcheck and both halves of `vectors-check` green.
- **4.2a `quorum_time` — the project's own specification was under-defined, and the test that proves it is four hundred seconds wide.**
  - **`GOSSIP.md` said "the *k-th newest* cosignature timestamp".** That is exactly right for a flat `group home 2 pi vps friend`, and it has **no meaning** once groups nest: `group top 1 inner friend` has no single k. The definition that survives both is *the latest instant T at which the witnesses who have signed by T satisfy the policy* — same answer for the flat case, defined for the rest. The doc now says that, with the k-th-newest reading kept as the intuition rather than the rule.
  - **The difference is a real number, not a quibble.** With `group inner 2 pi vps`, `group top 1 inner friend`, and signatures at pi=500, vps=400, friend=100: at 500 only pi has signed, so `inner` is short and `friend` is absent — nothing is satisfied. The answer is **400**, while "the 1st newest timestamp" says **500**. A node using the naive reading would believe a checkpoint is a hundred seconds fresher than any quorum vouched for. That case is a test.
  - **`quorum none` has no clock, and getting that backwards would be the dangerous way round.** A network that asked for no corroboration has nobody vouching for the *time* either — so freshness is `unknown`, not perfect. The easy mistake is to treat "policy satisfied by everyone, always" as "always fresh", which would hand a node a clock made of nothing.
  - **A witness the policy never named cannot move the clock**, however recent its cosignature. Same property as not being able to make up the quorum, and it needs its own test because it is a *different* code path: the quorum check happens once, the clock reads the same lines again.
  - **One mapping, not two.** A cosignature carries `norn-witness/pi` while the policy files that witness under `pi`; `logclient` had a private copy of that translation, and the clock needed it too. It is now `policy.Label`, where the two names already live side by side.
  - **A latent test bug surfaced the moment a pointer stopped being nil.** `back.Checkpoint != set.Checkpoint` compares a struct holding a `*int64` — which is address equality. It agreed for as long as both were `nil`, and would have gone on agreeing about nothing; it compares by value now.
  - `proven.json` publishes the instant the witnesses vouched for. The **state** computed from it — fresh, degraded, hard-stale — is 4.2b, so `freshness` still reads `unknown`: the reading exists, the machine that turns it into a claim about *now* does not yet.
- **4.2b the freshness machine — the wall clock is kept out by the type signature, not by a rule.**
  - **`Clock` is given durations, never timestamps.** It has no way to ask the operating system what time it is, so a node whose clock is wrong — or is moved while it runs — computes exactly the same age as one whose clock is right. That is A11 expressed as an API instead of as something a future edit has to remember, and it is the difference between a property and a comment. The agent test proves it from the outside: the wall clock lurches an hour forward between every cycle, and the view ages `fresh → degraded → hard_stale` on the monotonic reading alone.
  - **An older observation never moves the clock back.** A peer may legitimately serve a valid but older checkpoint; adopting its timestamp would drag the node's estimate of now backwards and make everything it holds look *newer* than it is — the one direction a freshness check must never fail in.
  - **A checkpoint older than the best one known is older**, and the age says so. Age is a property of what the node is *enforcing*, not of the best thing it has heard about, which matters precisely when a node is holding the last state that verified.
  - **The boundaries come from the log, and the fixture proved the point.** `staleness` is a §4.5 parameter, so a network agrees on when a view is too old; this fixture's log sets it to **900s** with a `params` entry, not §4.5's 600. The first version of the test asserted the default and failed — the log's own value is what a node must use, or it disagrees with the rest of its network about when to alarm. `S_hard` is the opposite: it drops every peer, so it stays a node-local decision (the same argument D-034 makes for the witness policy).
  - **`hard_stale` is computed but cannot yet be reached by a deployed node**, and that is deliberate rather than an oversight: `S_hard` is opt-in, defaults to off, and `nornd` has no flag for it. The state has no meaning apart from what the enforcer does about it, so the flag and the enforcement land together in **4.2d** — a state that drops every peer must not be reachable before the code that drops them exists.
  - **`proven.json` publishes the age as well as the state**, because a consumer that can only read a label cannot decide anything for itself, and the monitor's `norn_checkpoint_age_seconds` needs the number. Absent, not zero, when there is no clock.
  - **`norn status` stopped printing a hardcoded UNKNOWN.** It reports the instant a quorum vouched for as fact, and labels the age it derives as *this machine's clock* — a one-shot command has no monotonic history, so the honest thing is to name whose opinion the number is and say that the running daemon is what tracks the state.
  - **One set of state names.** `fresh`/`degraded`/`hard_stale`/`unknown` are defined where the machine is and aliased in `proven`, rather than spelled twice — two copies of a string constant is how a consumer matching on them quietly stops matching.
  - **A build failure that was not the code.** One suite run failed with `no required module provides package golang.org/x/mod/sumdb/tlog`, which passes in isolation; the module cache had been purged down to 16 MB because this machine's disk is at **99%** (3.2 GiB free). Worth writing down so the next flake of this shape is recognised as the disk rather than chased through the code.
  - Go: 42 packages, 411 tests; `go test`, staticcheck and both halves of `vectors-check` green.
- **4.2c `CLOCK_SKEW` — the documented formula reports a clock problem every time the log goes quiet.**
  - **`GOSSIP.md` said `|wall − quorum_time| > Δclock`.** That is the right number only at the instant a freshly cosigned head is fetched directly from the log. Away from that instant it measures the log's **staleness** as well: a log that has not been cosigned for two hours produces two hours on a node whose clock is perfect, and the node reports a clock fault. An operator following that alarm would go and "fix" the wrong machine while the actual problem — an unreachable log or a dead witness — went unnamed.
  - **The two are separable with what the node already has.** If its clock were right, `wall − quorum_time` would equal the monotonic age it has been measuring since adoption. The difference between them is the skew and nothing else, and it reduces to the documented expression exactly when the age is zero. `GOSSIP.md` now states that form, with the original kept as the special case it is.
  - **`GOSSIP.md`'s own T5 depends on the distinction**, which is how the defect was visible at all: a skewed node must raise `CLOCK_SKEW` and **not** go degraded. Its converse is the test that matters more — a genuinely stale log must go degraded and **not** raise `CLOCK_SKEW` — and both are now agent-level tests, not just unit ones.
  - **Both tests were run against the naive formula.** Substituting `wall.Sub(quorumTime)` turns the unit test and the agent test red, at both levels. A test that cannot tell the two implementations apart would have been decoration.
  - **The alarm changes nothing, and nothing downstream reads it.** Not the freshness state, not the proven set, not the peer table. A node that altered what it enforced because of its own clock would be doing the precise thing A11 forbids, so the only output is a line for a human.
  - **Δclock cannot be tight, and the reason is worth writing down.** At a direct fetch the newest cosignature is already one checkpoint interval plus a witness round trip old, so a threshold near zero would alarm on every healthy network. Five minutes absorbs that and still catches what this exists for: a dead RTC battery, a missing NTP server, a wrong time zone — failures measured in hours.
  - **It runs on the direct-from-log path only**, and the code says so where gossip will arrive: a checkpoint pulled from a peer may legitimately be older, and its age is the peer's business rather than evidence about this machine's clock.
  - **`norn status` still cannot report skew, and that is the honest answer.** A one-shot command has no monotonic history, so for it the ambiguity is real and irreducible — which is exactly why it prints "age by this machine's clock" and points at the running daemon.
  - **The one thing not shipped: the operator knobs.** `MaxSkew` and `Hard` are plumbed through `agent.Config` but `nornd` exposes neither, so Δclock is the 5-minute default and S_hard is off. The alarm is complete without a flag; a state that drops every peer is not, so both flags land with **4.2d**.
  - Go: 42 packages, 419 tests; `go test`, staticcheck and both halves of `vectors-check` green.
- **4.2d the freshness states do something — and hard-stale needed no new enforcement path at all.**
  - **`hard_stale` is "the proven set is empty".** `GOSSIP.md` part 5 spells out *owner: ReplacePeers []; watchdog: evict all*, and that is precisely what the existing reconciler already does for an empty desired set. So the state is implemented by passing one, not by a second enforcement path that could drift from the first. Both modes are tested, and observe still writes nothing however stale it gets.
  - **It says why, once.** An operator who found a dozen `UNPROVEN_PEER` lines and an empty interface would have no idea the cause was the clock, so `HARD_STALE` is emitted with the age before anything is dropped.
  - **The `degraded` alarm is on a cadence, and recovery resets it.** A daemon polling every minute must not produce a page a minute — but a degraded node that simply went *quiet* is indistinguishable from one that recovered, so it repeats every five minutes for as long as it lasts. Resetting on recovery is the part worth testing: carrying the suppression across would silence the next degradation for up to five minutes, which is exactly the transition an operator needs to see.
  - **An ordering bug, found by writing the test.** The cycle reconciled *before* observing the clock, so freshness could not have influenced enforcement at all — hard-stale would have dropped peers one cycle late, every time. How old the view is decides what reconciling is allowed to do, so it is now established first.
  - **A node's first sight of a checkpoint is age zero, and there is no way around it.** It has no history to measure against and its own clock is not evidence (A11), so a node that boots and fetches a three-day-old head calls it fresh. What it *can* say is `CLOCK_SKEW`: at a direct fetch, a large gap between wall time and witness time with an age of zero means either the clock is wrong or the log is ancient — and the node genuinely cannot tell which. That is an honest limit of refusing to trust the local clock, and the tests start the agent *running* rather than pretending otherwise.
  - **Opt-in twice.** `nornd` leaves S_hard unset unless asked, and **refuses a value below §4.5's `staleness` default** — that would drop every peer before the network had even called the view degraded, which is a typo with an outage attached. The flags are validated before the interface is opened, so a mistyped duration is reported as a configuration error rather than after a missing-interface one.
  - **Not done, and it belongs to gossip:** `degraded` should also "poll all sources every 10 s". With one source that is just polling the log harder; the sentence only means something once there are peers to poll, so it moves to **4.5**.
  - Go: 42 packages, 427 tests; `go test`, staticcheck and both halves of `vectors-check` green.
- **4.3a the `tlog-witness` client — checked against the specification's own bytes, and my first rule was wrong.**
  - **The protocol was fetched, not recalled**, which is the habit that found the algorithm-byte defect in 4.1a. `POST <prefix>/add-checkpoint`, body = `old <size>`, zero to 63 base64 consistency hashes, an empty line, then the checkpoint exactly as the log signed it.
  - **The test that matters is the document's own example request**, reproduced byte for byte. Everything else in the package checks it against itself; if the separator, the ordering, the base64 alphabet or a trailing newline were wrong *the same way* in the writer and the reader, only bytes somebody else wrote would ever notice.
  - **My own guard was wrong, and a test I wrote caught it.** I required a consistency proof whenever `old > 0`. But a proof from a size *to itself* is legitimately empty — which is exactly what resubmitting a head the witness has already cosigned looks like. The rule is keyed on the checkpoint's own size now: a proof is required when `0 < old < size`, and an `old` **ahead** of the checkpoint is this log's bug, refused here rather than sent to collect a `400`.
  - **`409` is the only refusal that carries data**, and it is the one the whole retry loop turns on: the witness answers with the size it last cosigned, so the log learns where to prove consistency from. It is a typed `ConflictError`, not a message, because a log that dropped the number would retry the same rejected request forever. A `409` whose body is *not* a size — a gateway error page — is an error rather than a guess.
  - **Every status is told apart, because each is a different thing to go and fix**: `404` the witness was never configured for this network, `403` it is configured for a different log key, `400` this log miscounted, `422` consistency could not be verified. That last one names the possibility worth checking first — **the log has forked and the witness is holding the other branch**.
  - **What comes back is verified before it is believed.** The protocol does not require a submitter to check, and a log that skipped it would publish whatever arrived: a head every verifier then refuses, with nothing log-side to say why. So a witness answering about some *other* checkpoint, or a middlebox rewriting one, is caught where it can still be reported — as is a `200` with an empty body, which is not success.
  - **An architecture test, because this is a boundary worth keeping.** `logclient`, `agent` and `nornd` may not import this package. A verifier reads cosignatures off the checkpoint it already has; one that dialled a witness would put a network round trip and a third party's availability on the path that decides whether a peer stays in the table.
  - **No new dependencies**: net/http and the packages Norn already has.
